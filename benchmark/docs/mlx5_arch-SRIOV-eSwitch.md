## 1. Core architecture Overview:

The mlx5_core Driver

The `mlx5_core` high performance network driver, manages Nvidia's CX (CX-5 - CX-7, BlueField SmartNICs,
and Grace Hopper/GB-10 integrated NICs) network devices.


- The driver exposes:
    - physical functions (PFs), 
    - handles control-plane commands, and 
    - configures hardware steering tables directly inside the NIC ASIC.
    
### The Hardware eSwitch (Embedded Switch)

Inside the CX NICs there is an eSwitch: Which is a HW L2/L3 packet classification and forwarding engine
embedded directly on the silicon.

```text

                          +-----------------------------------+
                          |        ConnectX / GB-10 ASIC      |
  Physical Wire <========>|  PF Port (enp1s0f0np0)            |
                          |                 |                 |
                          |        +-----------------+        |
                          |        |  Hardware       |        |
                          |        |  eSwitch Engine |        |
                          |        +-----------------+        |
                          |          /             \          |
                          |    VF 0 Port         VF 1 Port    |
                          +-------|-----------------|---------+
                                  |                 |
                             `enp1s0f0v0`      `enp1s0f0v1`
                             (Host/Guest)      (Host/Guest)
```

- All incoming physical wire traffic hits the eSwitch before reaching any host CPUs.
- All outgoing traffic generated by software (PFs or VFs) hits the eSwitch before going out to 
  the physical wire.
- The eSwitch decides whether to forward, drop, modify, or redirect packets using internal 
  Hardware Steering Tables.
  
- So eSwitch Mode defines how the NIC’s embedded HW switch routes traffic between VF's & PF's
  in an SR-IOV environment:
  1. Legacy Mode (Default):
    - Behavior: Operates as a basic hardware L2 MAC/VLAN switch.
    - Control: Managed using simple `ip link` settings on the PF.
    - Offloading: Limited no advanced packet manipulation, `tc flower`, or OVS HW offload support.
  2. Switchdev Mode:
    - Behavior: Unlocks the eSwitch into a fully programmable hardware pipeline.
    - Control: Creates VF Representors (r0) in the host namespace to represent VF control channels.
    - Offloading: Full offload—bridges like Open vSwitch or `tc flower` program steering rules 
      directly into the NIC ASIC for zero-CPU, wire-speed packet forwarding.
      

## 2. Legacy SR-IOV Mode

In Legacy Mode, the eSwitch operates as a simple, unconfigurable hardware MAC-learning switch 
or strict VLAN multiplexer.

```text
    +-------------------------------------------------------------------------+
    | HOST CPU / KERNEL                                                       |
    |                                                                         |
    |   +-------------------+    +-------------------+    +---------------+   |
    |   |   PF (Netdev)     |    |   VF 0 (Netdev)   |    |  VF 1 (Netdev)|   |
    |   |  `enp1s0f0np0`    |    |   `enp1s0f0v0`    |    |  `enp1s0f0v1` |   |
    |   +---------+---------+    +---------+---------+    +-------+-------+   |
    |             |                        |                      |           |
    +-------------|------------------------|----------------------|-----------+
    | HARDWARE    |                        |                      |           |
    |             v                        v                      v           |
    |      +---------------+       +---------------+      +---------------+   |
    |      |    PF Port    |       |  VF 0 Port    |      |   VF 1 Port   |   |
    |      +-------+-------+       +-------+-------+      +-------+-------+   |
    |              |                       |                      |           |
    |              +-----------------------+----------------------+           |
    |                                      |                                  |
    |                          [ eSwitch (Legacy Mode) ]                      |
    |                                      |                                  |
    |                             Physical Wire Port                          |
    +-------------------------------------------------------------------------+
```
**Key Properties**

- **Control Plane**: Minimal. Rules are applied via basic 
    `ip link set dev <PF> vf <ID> mac ... vlan ...` commands.

- **Datapath**: Switching is restricted to basic destination MAC matching.

- **Offloading Limitations**: You cannot apply complex OpenFlow rules, stateful firewalling, or 
   advanced tc flower offloads to VF traffic.
   
- **Visibility**: The host driver cannot monitor or manipulate individual VF traffic streams 
  locally unless explicitly mirroring the port.
  
  
## 3. Switchdev SR-IOV Mode

In Switchdev Mode, the eSwitch is unlocked into an open, fully programmable packet-processing pipeline.

```text

    +---------------------------------------------------------------------------------------+
    | HOST ROOT NAMESPACE (Control Plane / OVS / TC)                                        |
    |                                                                                       |
    |   +-------------------+    +-----------------------+    +-----------------------+     |
    |   |   PF (Netdev)     |    | VF 0 Representor (r0) |    | VF 1 Representor (r1) |     |
    |   |  `enp1s0f0np0`    |    |     `enp1s0f0r0`      |    |     `enp1s0f0r1`      |     |
    |   +---------+---------+    +-----------+-----------+    +-----------+-----------+     |
    |             |                          |                            |                 |
    |             |              +-----------+----------------------------+                 |
    |             |              |  Software Control (OVS / tc flower)    |                 |
    |             |              +-----------+----------------------------+                 |
    +-------------|--------------------------|----------------------------|-----------------+
    | HARDWARE    |                          | (Pushes Flow Rules)        |                 |
    |             v                          v                            v                 |
    |      +---------------+       +--------------------+       +--------------------+      |
    |      |  PF Uplink    |       |  VF 0 Rep Port     |       |  VF 1 Rep Port     |      |
    |      +-------+-------+       +---------+----------+       +---------+----------+      |
    |              |                         |                            |                 |
    |              +-------------------------+----------------------------+                 |
    |                                        |                                              |
    |                         [ eSwitch (Switchdev Mode) ] <--- Fastpath Offload            |
    |                                 /              \                                      |
    |                        VF 0 Data Port        VF 1 Data Port                           |
    +------------------------------|----------------------|---------------------------------+
                                |                      |
                            To guest/netns         To guest/netns
                            (`enp1s0f0v0`)         (`enp1s0f0v1`)
```

### The Concept of Representors (r0)

Switching a interface to switchdev, the kernel creates a VF Representor interface (e.g., enp1s0f0r0) 
in the host root namespace for every allocated VF.

- This VF Representor is a control plain pipe to the hardware VF port.
- How does the traffic flow:
    - Exception packets (unhandled flows) sent by VF 0 arrive at enp1s0f0r0 for host CPU processing.
    - Any packet injected into enp1s0f0r0 by the host CPU pops out of VF 0 (enp1s0f0v0).
    
- Why Representors exists: Software bridges like Open vSwitch (OVS) or kernel `tc` attach to
  representors (r0) to program steering rules directly into the hardware eSwitch.
  

## 4. Legacy vs. Switchdev Comparison

| Feature | Legacy Mode | Switchdev Mode |
| :--- | :--- | :--- |
| eSwitch Role | Simple MAC/VLAN Multiplexer | Fully programmable eSwitch     |
| VF Control   | Basic ip link settings      | VF Representor interfaces (r0) |
| SW Bridge Integration |Not supported for HW offload | "Supported (OVS, tc flower, Linux bridge)"|
| HW Offloading | None (SR-IOV bypass only) | "Full packet header manipulation, forwarding, mirror, dropped flows"|
| CPU Overhead | Zero (if simple forwarding) | Zero (after initial flow rule lookup) |
| Primary Use Case | Basic VM static network access | "Cloud, Telco (OpenStack, Kubernetes Kube-OVN), SmartNIC offload"|

## 5. Mode Switch Commands

- Check Current Mode 
```bash
    $ sudo devlink dev eswitch show pci/0000:01:00.0
```

- Unbind VFs and Enable Switchdev Mode: 
  There are two methods of unbinging:
  
  1. Using Driver unbinging ( `unbind` / `bind` ):
     This method keeps the VFs allocated at the PCI level, but detaches the `mlx5_core`
     kernel driver from the VF PCI addresses before executing the `devlink` mode change.
     
    ```bash
        #1. Ensure zero VFs are active before mode switch
        echo 0 > /sys/class/net/enp1s0f0np0/device/sriov_numvfs

        #2. Change mode to switchdev via devlink
        devlink dev eswitch set pci/0000:01:00.0 mode switchdev

        #3. Enable hardware TC offload on PF
        ethtool -K enp1s0f0np0 hw-tc-offload on

        #4. Re-instantiate desired VFs
        echo 2 > /sys/class/net/enp1s0f0np0/device/sriov_numvfs
    ```
  2.  VF Re-creation (sriov_numvfs=0)
  This method completely destroys the VFs in sysfs, changes the eSwitch mode on the clean PF, 
  and then recreates the VFs under the new mode.

  ```bash 
    # 1. Destroy VFs
    echo 0 > /sys/class/net/enp1s0f0np0/device/sriov_numvfs
    
    # 2. Switch eSwitch to switchdev
    devlink dev eswitch set pci/0000:01:00.0 mode switchdev
    
    # 3. Re-create VFs
    echo 2 > /sys/class/net/enp1s0f0np0/device/sriov_numvfs
  ```
| Feature | Unbind / Bind (Method A) | Destroy / Re-create (Method B) |
| :--- | :--- | :--- |
| PCI Addresses | "Preserved. The VF PCI BDFs (e.g., 0000:01:00.2) remain assigned." | Dynamic. May change or reset depending on the PCIe bus topology. |
| VM Passthrough | Preferred if passing VFs into running QEMU/KVM VMs via vfio-pci. | Destroys PCI nodes; requires VM re-initialization| 
| Ease of Scripting | Requires knowing the exact PCI BDF addresses of every VF. | Simpler—just needs the PF interface name. |
| Reliability | Can fail if a guest VM or netns holds an active lock on the VF.| "Guaranteed clean slate, as all VFs are destroyed first." |
  
  - Use sriov_numvfs=0 method: When writing bare-metal provisioning scripts, testing automation, or
   setting up host netns environments. It is cleaner and less error-prone.
  
  - Use unbind / bind method: When working with DPDK workloads, KVM/QEMU hypervisors, or orchestration
    systems (like OpenStack/Nova) where PCI devices are pre-allocated to guest domains and cannot be
    destroyed.
  
- Revert to Legacy Mode
```bash
    echo 0 > /sys/class/net/enp1s0f0np0/device/sriov_numvfs
    devlink dev eswitch set pci/0000:01:00.0 mode legacy
    echo 2 > /sys/class/net/enp1s0f0np0/device/sriov_numvfs
```

# ConnectX eSwitch Modes, mlx5 Driver Behavior, and Representors — A Practical Tutorial ( claud )

## 1. Why the eSwitch mode is the root concept

Every ConnectX SmartNIC with SR-IOV enabled has an **embedded switch (eSwitch)** sitting inside the NIC ASIC, between the physical port(s) and the PF/VFs. The eSwitch is what decides where a packet goes once it leaves the wire or leaves a VF. Everything else — how the `mlx5_core` driver exposes netdevs, how VF policy is configured, how OVS/TC offload works, whether representors exist at all — is downstream of **which mode the eSwitch is in**. If you don't know the mode, you can't reason correctly about traffic behavior; this is almost certainly why the earlier debugging threads went sideways.

There are two modes:

| | Legacy | Switchdev |
|---|---|---|
| eSwitch behavior | Simple embedded L2 switch (MAC/VLAN matching in FW) | Programmable forwarding via a Forwarding DataBase (FDB) |
| VF control path | `ip link set <pf> vf <n> ...` | `devlink port function ...` + representor netdevs |
| Representors | None | One per VF/SF + one uplink representor |
| Steering | Fixed FW logic | TC flower rules, offloaded to hardware (ASAP²) |
| Typical use | Basic SR-IOV passthrough | OVS/TC hardware offload, NFV, cloud-native networking |

## 2. Legacy mode

In legacy mode, the eSwitch does exactly what its name implies: forwards packets based on the VF's assigned MAC address and VLAN, enforced in firmware. From the host's point of view:

- The PF netdev exists; VFs are visible as PCI functions bound (typically) to `mlx5_core` inside the guest/container.
- There is **no representor netdev** for each VF — the host has no direct hook into individual VF traffic.
- Policy is set per-VF via classic iproute2:

```bash
ip link set eth0 vf 0 mac 00:11:22:33:44:55
ip link set eth0 vf 0 vlan 100
ip link set eth0 vf 0 spoofchk on
ip link set eth0 vf 0 trust on
ip link set eth0 vf 0 rate 1000   # Mbps
```

- Forwarding decisions (which VF a packet goes to, whether it's allowed out) are made entirely in firmware state machines — the kernel networking stack (TC, netfilter, OVS datapath) never sees this traffic on the host.

This is fine for simple SR-IOV passthrough (VM gets a VF, done), but it gives you **no programmability and no visibility** on the host side. You cannot attach ACLs, bridges, or flow rules to individual VF traffic in legacy mode beyond what the limited VF-trust/spoofchk/VLAN knobs expose.

## 3. Switchdev mode

Switchdev mode turns the eSwitch into something you program, using the kernel's generic `switchdev` subsystem (the same framework used by physical switch ASIC drivers). This is the mode ASAP² (Accelerated Switching and Packet Processing) relies on.

Key structural change: **each VF/SF gets a corresponding representor netdev on the host (or on the embedded ARM cores if it's a BlueField DPU)**, plus one **uplink representor** for the physical port.

### 3.1 The representor contract

A representor is a lightweight netdev that mirrors a VF/SF 1:1:

- A packet **sent by the VF** appears as an **ingress** packet on its representor (assuming no offloaded flow intercepts it first).
- A packet **sent into the representor** (from the host stack, OVS, or a bridge) is **transmitted out the VF**.

This gives the host a physical-switch-port abstraction for every VF: you can bridge it, apply `tc` rules to it, run OVS on it, monitor it with `tcpdump`, etc., exactly as if it were a physical cable to that VF.

### 3.2 Enabling switchdev mode

```bash
# 1. Unbind all VFs first (VMs using them must be powered off / VFs detached)
echo 0000:04:00.2 > /sys/bus/pci/drivers/mlx5_core/unbind
echo 0000:04:00.3 > /sys/bus/pci/drivers/mlx5_core/unbind

# 2. Switch the PF's eSwitch mode
devlink dev eswitch set pci/0000:04:00.0 mode switchdev

# 3. Rebind
echo 0000:04:00.2 > /sys/bus/pci/drivers/mlx5_core/bind
echo 0000:04:00.3 > /sys/bus/pci/drivers/mlx5_core/bind
```

This single `devlink` command is what creates the VF representor netdevs on the host. To go back:

```bash
devlink dev eswitch set pci/0000:04:00.0 mode legacy
```

Note the ordering dependency that trips people up: **VFs must exist (`sriov_numvfs > 0`) before or independent of the mode switch, but they must be unbound while the mode itself is changing.** Switching mode with VFs actively bound to drivers, or with existing offloaded flows/SFs still configured, is a common failure ("Error: mlx5_core: Can't change mode when flows are configured").

### 3.3 Identifying representors

Representors show up as regular netdevs (`enp...`, `eth...`, or `pf0vf0`-style names depending on udev/naming scheme). Map a representor to its VF via `switchid` + `portname`:

```bash
ip -d link show eth4
# ... portname pf0vf1 switchid f4ab580003a1420c
```

- `switchid` — identifies which physical eSwitch/ASIC this representor belongs to (matters on multi-port/dual-PF cards).
- `portname` — tells you exactly which PF/VF it represents (`pf0vf1` = PF0, VF1). The **uplink representor** (representing the physical port itself, e.g. `p0`) is a special one: it looks like a normal netdev but cannot host an IP address or be pinged — it's meant to be enslaved to a bridge/OVS/bond, not used as an L3 interface.

### 3.4 Where the driver logic actually lives

This maps directly onto the `mlx5_core` source tree, if you want to go deeper than the docs:

- `drivers/net/ethernet/mellanox/mlx5/core/eswitch.c` — mode state machine, legacy vs offloads (switchdev) dispatch.
- `drivers/net/ethernet/mellanox/mlx5/core/eswitch_offloads.c` — switchdev-specific FDB rule management, representor lifecycle.
- `drivers/net/ethernet/mellanox/mlx5/core/en_rep.c` — representor netdev implementation (the `ndo_start_xmit`/rx path that gives you the "packet in = packet out the VF" behavior).
- `Documentation/networking/device_drivers/ethernet/mellanox/mlx5/switchdev.rst` (rendered at the kernel docs link above) — the closest thing to a spec.

## 4. What actually steers traffic in switchdev mode: the FDB

Once representors exist, **traffic is not automatically forwarded anywhere**. This is the single most common cause of "it just doesn't work" symptoms:

- With **no rules installed**, packets arriving on a representor go to the **kernel's slow path** by default (up through the representor netdev into the normal Linux networking stack) — they are not switched at wire speed until you explicitly program forwarding.
- To get hardware-accelerated forwarding, you populate the eSwitch's FDB (Forwarding DataBase) by:
  1. Enslaving representors to a Linux bridge or an OVS bridge, **or**
  2. Installing explicit `tc flower` rules with hardware offload flags.

### 4.1 Minimal working example: Linux bridge

```bash
ip link add name br0 type bridge
ip link set p0 master br0        # uplink representor
ip link set pf0vf0 master br0    # VF0 representor
ip link set pf0vf1 master br0    # VF1 representor
ip link set br0 up
ip link set p0 up
ip link set pf0vf0 up
ip link set pf0vf1 up
```

Recent kernels (with `switchdev` bridge offload support) will push this bridging into hardware automatically once all member ports share the same `switchid`.

### 4.2 TC flower offload (OVS or manual)

```bash
tc qdisc add dev pf0vf0 ingress
tc filter add dev pf0vf0 protocol ip parent ffff: \
    flower skip_sw dst_ip 10.0.0.5 \
    action mirred egress redirect dev pf0vf1
```

- `skip_sw` forces the rule to be hardware-offloaded (fails if it can't be); `skip_hw` forces software-only. Omitting both lets the kernel try hardware first and fall back to software.
- OVS with hw-offload enabled (`ovs-vsctl set Open_vSwitch . other_config:hw-offload=true`) does this automatically for every flow it installs on representor ports.

### 4.3 Tunnels / encap

If you're offloading VXLAN or other tunnel traffic, encap support has to be explicitly turned on:

```bash
devlink dev eswitch set pci/0000:04:00.0 mode switchdev encap basic
```

Without this, tunnel-related flows silently stay in the software path even though everything else looks correctly offloaded — a classic "steering looks right but performance is wrong" bug.

## 5. Failure patterns and how they map back to eSwitch mode misunderstanding

Given the "traffic behavior failing in many cases" you mentioned, these are the most likely root causes, roughly in order of how often they bite people:

1. **Debugging in switchdev mode using legacy-mode mental model** — expecting `ip link set vf ...` commands to affect anything once you're in switchdev; they mostly don't (VF policy in switchdev goes through `devlink port function` instead).
2. **Representors created but never enslaved / no FDB rules** — traffic looks "stuck" or goes through the slow path with unexpected latency/throughput, because nothing told the eSwitch where to forward it.
3. **Mode switched with stale state** — VFs still bound, SFs still present, or old flows still installed block the mode transition entirely, or leave the driver in an inconsistent internal state (this was literally still being patched upstream as of Feb 2026 — see the kernel patch on `MLX5_PRIV_FLAGS_SWITCH_LEGACY` not being cleared on legacy→switchdev transitions, which caused stale legacy-mode bookkeeping to persist).
4. **Encap mode not enabled** — tunnel flows silently fall back to software, masquerading as a "performance" issue rather than a "config" issue.
5. **Multi-PF / dual-port cards** — forgetting to set eswitch mode identically on *both* PCI functions (`0000:08:00.0` and `0000:08:00.1`), leading to asymmetric behavior.
6. **Flow steering mode (DMFS vs SMFS)** — affects rule scaling and matters more under switchdev with many offloaded flows; worth checking if you're hitting scale limits rather than correctness bugs.

## 6. Suggested debugging workflow

1. **Confirm current mode** on every relevant PF:
   ```bash
   devlink dev eswitch show pci/0000:04:00.0
   ```
2. **Confirm representors exist and map correctly**:
   ```bash
   ip -d link show | grep -A2 portname
   ```
3. **Check whether anything is actually enslaved/bridged** — representors with no master and no tc filters will pass nothing at hardware speed.
4. **Check offload status of flows** (OVS):
   ```bash
   ovs-appctl dpctl/dump-flows type=offloaded
   ```
5. **Check for encap mode** if tunnels are involved.
6. **Check dmesg** for eSwitch errors on any mode transition (`Can't change mode when flows are configured` is the most common one).
