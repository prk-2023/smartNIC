To understand how one physical port appears in two different places, it helps to look at how the Nvidia Grace Hopper or Grace Blackwell Superchip is built.
Here is the breakdown of how this mirroring works and what the different "sides" mean.
## What is "Grace-side" vs. "GPU-side"?
A standard computer has one motherboard, one CPU, and a PCIe slot for a GPU. A Nvidia Superchip is different. It puts a CPU and a GPU right next to each other on the same board, connected by a high-speed highway called NVLink-C2C. [1, 2, 3, 4]
Because they are so powerful, they act like two separate computers living on the same chip: [5]

* Grace-side (CPU Domain): This is the Arm-based "Grace" CPU running your standard operating system (like Ubuntu). It handles standard OS tasks, storage, and traditional network traffic.
* GPU-side (SoC / BlueField Domain): This is the "Hopper" or "Blackwell" GPU side. In these architectures, the network card (ConnectX-7 or BlueField-3) is directly wired to the GPU's internal PCIe switch. [6, 7]

## What does "Mirrored Across PCI Domains" Mean?
In a normal PC, a network card plugs into one PCIe slot. The CPU sees it, assigns it a single address (like enp1s0f0), and that is it.
On a DGX Superchip, the network card is a Multi-Host NIC. It physically has wires running to both the CPU and the GPU at the same time.
Because the CPU and the GPU have their own separate PCIe environments (called PCI Domains), they cannot see each other's internal paths. Therefore, the network card exposes itself twice: [8, 9, 10]

   1. Domain 0000 (Grace CPU): The OS sees a network interface (enp1s0f0np0).
   2. Domain 0002 (GPU / Switch): The OS sees a second network interface (enP2p1s0f0np0).

They have different names because they are coming down different physical PCIe wires, but they terminate at the exact same physical Ethernet or InfiniBand port on the back of the machine.
## Why do they do this?
There are two major reasons for this architectural design:

* Bypassing the CPU for Speed (RDMA): When the GPU needs to talk to another server over the network, it does not want to ask the Grace CPU for help. That wastes time. Because the port is "mirrored" on the GPU side, the GPU can send data straight out the physical port. [11]
* Getting Around Bandwidth Limits: A single internal connection on the chip might not be wide enough to support the massive 200Gbps or 400Gbps speed of the network port. By splitting the traffic across two different PCIe domains (e.g., two ×4 links), the system combines them to get full network speed.

When you connect a DAC cable directly as a crossover loopback between Port 0 and Port 1 on the exact same NVIDIA DGX network card (ConnectX-7), Layer 2 (L2) traffic passes through at the physical layer, but the operating system drops the packets.
The physical link lights will turn green and state UP, but you will not be able to ping or broadcast L2 traffic between the ports. This behavior stems from three specific architectural features of NVIDIA multi-host networking: [1]
## 1. Internal eSwitch Loopback Blocking
Inside a ConnectX-7 ASIC, there is an embedded hardware switch (called an eSwitch).

* When you attempt to route traffic from Port 0 to Port 1 on the same card, the ASIC's eSwitch notices that the destination MAC address or route belongs to its own hardware footprint. [1]
* Instead of pushing the packet out through the physical laser/copper of Port 0 and back into Port 1 via the DAC, the internal eSwitch logic attempts to short-circuit the path internally. [2]
* Because external loopback/crossover routing creates a massive risk for infinite L2 network loops, the ConnectX firmware deliberately blocks or drops self-destined traffic moving across its own physical port boundaries unless explicitly configured in a diagnostic mode. [2]

## 2. Linux Kernel "Martian" Packet Filtering
Because the ports are mirrored across two PCI domains, the Linux operating system sees Port 0 and Port 1 twice. When you send a packet out of enp1s0f0np0 (Port 0) and it loops into enp1s0f1np1 (Port 1), the Linux kernel panics at the routing layer: [3, 4]

* The kernel receives a packet on Port 1, but its internal routing table says that the source IP/MAC address belongs to Port 0—which is hosted on the exact same operating system instance.
* The Linux networking stack identifies this as an asymmetric routing violation (Martian packet). It assumes a malicious spoofing attempt or a critical network loop is occurring, and silently drops the packet before it can pass through Layer 2 into application memory.

## 3. Multi-Host Shared MAC Context
In a DGX multi-host architecture, the two physical ports share a unified ASIC boundary. When you pass L2 traffic over a crossover cable on the same card, the hardware struggles to differentiate between a genuinely unique external endpoint and itself. The ASIC cannot simultaneously register the same local MAC contexts acting as both the ingress and egress authority on a shared hardware plane.
## How to Bypass This (For Testing)
If you are doing this crossover setup to run diagnostic or throughput loopback tests, you have to explicitly tell the hardware to allow it:

   1. Disable Linux Reverse Path Filtering: Instruct the OS to stop dropping packets that originate from its own subnets on different interfaces:

   sysctl -w net.ipv4.conf.all.rp_filter=0
   sysctl -w net.ipv4.conf.default.rp_filter=0

   2. Enable Firmware External Loopback Mode: You must use the NVIDIA Mellanox Firmware Tools (MFT) to force the ASIC to ignore the internal eSwitch and send traffic directly out to the cable:

   # Use mlxlink to force external loopback behavior on the ports
   mlxlink -d <your_device_pcie_address> --loopback EX

   [2]

Are the above setting retian on reboots?

No, the firmware external loopback mode set via mlxlink does not retain on a system reboot. [1]
The mlxlink tool operates dynamically on the live hardware registers. Once the DGX system reboots, power cycles, or the Mellanox driver unloads/reloads, the ConnectX-7 ASIC automatically resets its runtime registers back to their default state. [2, 3, 4]
## How to Revert the Setting Without Rebooting
If you finish your testing and want to immediately revert to standard production networking without wasting time on a full system reboot, you can clear the loopback config manually using the MFT suite: [5]

   1. Bring the physical port state down:
   On ConnectX-7 and newer ASICs, changing loopback states requires the link state to be fully down (not polling).

   mlxlink -d <your_device_pcie_address> --port_state DN

   2. Clear the loopback configuration:
   Pass the NO argument to explicitly disable the loopback mode.

   mlxlink -d <your_device_pcie_address> --loopback NO

   3. Bring the physical port back up:

   mlxlink -d <your_device_pcie_address> --port_state UP

   [3, 6]

## Persistent Alternative (Warning)
If you ever mistakenly use mlxconfig (instead of mlxlink) to alter physical layer configurations or write parameters to the non-volatile database using flags like --database, those changes will persist across reboots. If you suspect a setting was saved permanently, you can query or clear it via: [7]

# Check the persistent NVRAM config for loopback or link settings
mlxconfig -d <your_device_pcie_address> query
# Reset the entire ConnectX-7 adapter back to official factory defaults
mlxconfig -d <your_device_pcie_address> reset

Using network namespaces works without changing the mlxlink hardware loopback settings because it completely bypasses the Linux Kernel "Martian" Packet Filtering layer.
However, there is an important catch regarding how the traffic actually flows. Here is exactly what happens under the hood when you use namespaces. [1]
## 1. It Solves the OS Routing Problem (No More Martians)
In a standard configuration, the Linux kernel controls all network interfaces in a single, shared routing table. When you try to loop a packet from Port 0 to Port 1, the kernel sees a packet arrive on Port 1 that claims to be from an IP address owned by Port 0 (the same OS). It assumes a loop or a security attack and drops it instantly. [2]
When you isolate Port 0 into Namespace_A and Port 1 into Namespace_B:

* Each namespace acts as a completely independent router with its own isolated network stack, routing table, and ARP cache.
* Namespace_B has absolutely no knowledge that Port 0 exists or what its IP/MAC address is.
* When the packet arrives, the kernel treats it exactly like a packet coming from a completely separate physical computer. The "Martian" filter is never triggered. [3, 4, 5, 6, 7]

## 2. The Catch: The Traffic Never Leaves the Card (Internal eSwitch)
While network namespaces solve the Linux kernel problem, they do not force the traffic to go out through your physical DAC cable. [8]
Inside the ConnectX-7 card, the embedded hardware switch (eSwitch) is constantly monitoring the MAC addresses of its ports.

* When Namespace_A sends a packet out of Port 0 destined for Port 1, the packet hits the ConnectX-7 ASIC.
* The ASIC looks at the destination MAC address, recognizes that it owns Port 1, and routes the data internally within the chip's silicon.
* The traffic is handed straight over to Port 1 and climbs up into Namespace_B.

## Why Your Setup "Works" (But Isn't Using the Cable)
Because the internal eSwitch handles the loopback perfectly inside the chip, you will successfully be able to ping, run iperf3, and pass L2 traffic between the namespaces.
The link lights on your DAC cable will be green, but no actual data packets are traveling through the physical copper/optical fibers of the DAC. The DAC is merely serving as a dummy plug to trick the firmware into thinking the physical link is UP. If you unplug the DAC, the link state drops to DOWN, the eSwitch disables the interfaces, and the communication stops. [9]
## Summary of the Difference

| Method | Does Traffic Go Through the DAC Cable? | Requires Firmware Loopback? | Why it Works |
|---|---|---|---|
| Standard OS (No Namespaces) | No (Blocked by OS & Hardware) [3] | Yes (Requires mlxlink EX) [3] | Overrides both OS routing drops and hardware eSwitch blocking. |
| Network Namespaces | No (Short-circuited inside the chip) | No | Bypasses OS routing filters; hardware automatically routes it internally. |

If you are using this setup to test your application logic or software stack, network namespaces are perfect and highly efficient. However, if you are trying to test the physical health, signal integrity, or maximum throughput of the physical DAC cable, you must use the mlxlink --loopback EX method.

==== Script to force loopback EX mode ====



#!/bin/bash

# Ensure the script is run as root
if [ "$EUID" -ne 0 ]; then
  echo "[!] Please run this script with sudo or as root."
  exit 1
fi

# ==========================================
# CONFIGURATION VARIABLES
# ==========================================
# PCIe Device Addresses
DEV_0="0000:01:00.0"
DEV_1="0000:01:00.1"

# OS Interface Names
INT_0="enp1s0f0np0"
INT_1="enp1s0f1np1"

# IP Address Network Configuration
IP_0="10.0.1.1"
IP_1="10.0.2.1"
NETMASK="/24"

echo "=========================================================="
echo " Starting ConnectX-7 External Loopback Configuration"
echo "=========================================================="

# 1. SHUT DOWN INTERFACES AT OS AND FIRMWARE LAYER
echo "[*] Step 1: Bringing down OS interfaces and forcing physical link down..."
ip link set "$INT_0" down
ip link set "$INT_1" down
mlxlink -d "$DEV_0" --port_state DN > /dev/null 2>&1
mlxlink -d "$DEV_1" --port_state DN > /dev/null 2>&1
sleep 2

# 2. FORCE SPEED & DISABLE AUTO-NEGOTIATION (Prerequisite for EX Loopback)
echo "[*] Step 2: Disabling hardware auto-negotiation (forcing link mode)...Make sure to pass correct link speed format"
mlxlink -d "$DEV_0" --link_mode_force --speed 100G_2X > /dev/null 2>&1
mlxlink -d "$DEV_1" --link_mode_force > --speed 100G_2X /dev/null 2>&1

# 3. ENGAGE HARDWARE LEVEL EXTERNAL LOOPBACK MODE
echo "[*] Step 3: Enabling External Loopback (EX) on firmware registers..."
mlxlink -d "$DEV_0" --loopback EX > /dev/null 2>&1
mlxlink -d "$DEV_1" --loopback EX > /dev/null 2>&1

# 4. WAKE THE PHYSICAL AND LOGICAL LAYER BACK UP
echo "[*] Step 4: Powering up ports and bringing up OS interfaces..."
mlxlink -d "$DEV_0" --port_state UP > /dev/null 2>&1
mlxlink -d "$DEV_1" --port_state UP > /dev/null 2>&1
ip link set "$INT_0" up
ip link set "$INT_1" up
sleep 3

# Verify hardware accepted the state change
LB_STATUS_0=$(mlxlink -d "$DEV_0" | grep -i "Loopback Mode" | awk -F ':' '{print $2}' | xargs)
LB_STATUS_1=$(mlxlink -d "$DEV_1" | grep -i "Loopback Mode" | awk -F ':' '{print $2}' | xargs)
echo "    -> Firmware Port 0 Status: $LB_STATUS_0"
echo "    -> Firmware Port 1 Status: $LB_STATUS_1"

# 5. IP AND NETWORK LAYER SETUP
echo "[*] Step 5: Flushing legacy IPs and assigning isolated subnets..."
ip addr flush dev "$INT_0"
ip addr flush dev "$INT_1"
ip addr add "${IP_0}${NETMASK}" dev "$INT_0"
ip addr add "${IP_1}${NETMASK}" dev "$INT_1"

# 6. STATIC INTERFACE ROUTING (Forces data over the PCIe boundaries)
echo "[*] Step 6: Injecting point-to-point hardware static routes..."
ip route add "$IP_1" dev "$INT_0"
ip route add "$IP_0" dev "$INT_1"

# 7. CRITICAL KERNEL OVERRIDES (Bypassing routing/cross-talk drop behaviors)
echo "[*] Step 7: Applying Linux sysctl overrides (rp_filter & accept_local)..."
sysctl -w net.ipv4.conf.all.rp_filter=0 > /dev/null
sysctl -w net.ipv4.conf.default.rp_filter=0 > /dev/null
sysctl -w net.ipv4.conf."$INT_0".rp_filter=0 > /dev/null
sysctl -w net.ipv4.conf."$INT_1".rp_filter=0 > /dev/null
sysctl -w net.ipv4.conf."$INT_0".accept_local=1 > /dev/null
sysctl -w net.ipv4.conf."$INT_1".accept_local=1 > /dev/null

# 8. EXTRACT MAC ADDRESSES AND INJECT STATIC ARP ENTRIES
echo "[*] Step 8: Dynamically binding hardware MAC addresses to bypass ARP..."
MAC_0=$(cat /sys/class/net/"$INT_0"/address)
MAC_1=$(cat /sys/class/net/"$INT_1"/address)

if [ -z "$MAC_0" ] || [ -z "$MAC_1" ]; then
    echo "[!] Error: Failed to extract MAC addresses. Ensure interfaces are up."
    exit 1
fi

echo "    -> Extracted $INT_0 MAC: $MAC_0"
echo "    -> Extracted $INT_1 MAC: $MAC_1"

# Apply the cross-mapped static ARP keys
arp -i "$INT_0" -s "$IP_1" "$MAC_1"
arp -i "$INT_1" -s "$IP_0" "$MAC_0"

echo "=========================================================="
echo " Setup Completed Successfully!"
echo "=========================================================="
echo " Diagnostic Ping Command to test:"
echo "   ping -I $INT_0 $IP_1 -c 3"
echo "=========================================================="

sudo mlxlink -d 0000:01:00.0 | grep -i loopback
sudo mlxlink -d 0000:01:00.1 | grep -i loopback

## Standard PCIe hierarchy (with multiple domains) 

```
[ CPU / System Memory ]
   │
   ├─► [ PCIe Domain 0000 ] (Root Complex 1)
   │      │
   │      ├─► [ Root Port 0000:00:01.0 ]
   │      │      └─► [ Bus 01 ] ──► [ GPU (0000:01:00.0) ]
   │      │
   │      └─► [ Root Port 0000:00:02.0 ]
   │             └─► [ Bus 02 ] ──► [ PCIe Switch ]
   │                                   │
   │                                   ├─► [ Downstream Port 1 ] ──► [ NVMe SSD 1 (0000:03:00.0) ]
   │                                   └─► [ Downstream Port 2 ] ──► [ NVMe SSD 2 (0000:04:00.0) ]
   │
   └─► [ PCIe Domain 0001 ] (Root Complex 2 / Second CPU Socket)
          │
          └─► [ Root Port 0001:00:01.0 ]
                 └─► [ Bus 01 ] ──► [ 100G NIC (0001:01:00.0) ]
```

Key Elements ExplainedRoot Complex: The bridge between the CPU/memory and the PCIe fabric.
Domain: The highest isolation level (e.g., 0000 vs 0001), bypassing the 256-bus limit per tree.
Root Ports: The individual PCIe slots or lanes coming directly out of the Root Complex.
Switches: Packet routers that expand a single port to connect multiple downstream endpoints.
Endpoints: The actual hardware devices (GPU, NVMe, NIC) at the leaf nodes of the tree. 

## How Linux maps PCIe topology:

Linux maps PCIe topologies into clear paths using a standard address structure, a specialized virtual fs, 
and strict hardware discovery during boot.

### The Address Format (BDF)
Linux identifies every unique PCIe path using the `Segment:Bus:Device.Function` (SBDF) format. 
It appears in tools like lspci as 0000:00:01.0:

* Segment (Domain): 16-bit hex (0000 to ffff). Identifies the independent Root Complex tree.
* Bus: 8-bit hex (00 to ff). A single domain can hold up to 256 buses.
* Device: 5-bit hex (00 to 1f). Represents a physical chip slot on that bus.
* Function: 3-bit hex (0 to 7). Pinpoints a sub-component within a multi-functional device. [1] 

### The Sysfs Virtual Directory Tree
Linux exposes the exact hardware tree structure to user space inside the /sys/devices directory. 
The folder hierarchy mirrors your physical hardware tree layout. [2, 3] 
A path to a GPU looks like this:
/sys/devices/pci0000:00/0000:00:01.0/0000:01:00.0/

* pci0000:00: Represents Domain 0000, Bus 00 (The Root Bus).
* /0000:00:01.0: Represents the Root Port bridge device on that root bus.
* /0000:01:00.0: Represents the actual GPU sitting on Bus 01 downstream from that bridge. [4] 

### The Boot Discovery Process

   1. ACPI Scan: At boot, the Linux kernel queries the motherboard's ACPI tables (MCFG table).
   2. Domain Allocation: The kernel reads the tables to learn how many independent Root Complexes exist and assigns them domain numbers.
   3. Depth-First Enumeration: The kernel scans Bus 0, finds bridges (Root Ports), assigns them a secondary bus number, and immediately dives down to scan that new bus before returning to the parent level.
   4. Driver Binding: Once the entire tree is mapped in memory, the kernel matches vendor IDs to load the correct device drivers.

To see this mapping visually on your machine, you can run lspci -t to output a live text tree, or use ls -d /sys/devices/pci* to see your system's domains. [5]
